# CodeXX rules registry

Published, versioned rules for **`codegen`** — the C++ code-generation tool of the
[CodeXX DTDK](https://www.codexx-dtdk.com). Browse a rule, copy it into your project,
edit it to taste.

> Rules are published **only through pull requests**. There is no self-service publish
> command, by design — review is what keeps the catalog worth reading, and it is how
> authors get credited.

## Prerequisites

Install `codegen` and make sure it is on your `PATH`:

```sh
codegen --version
```

See the [installation guide](https://www.codexx-dtdk.com/docs/getting-started/installation)
if you don't have it yet.

## Using a rule

Rules are namespaced by vendor, so two authors can both publish a `ToString`:

```
rules/<kind>/<vendor>/<RuleName>/
```

**Copy the rule directory into your own project.** This is the normal way to use the
registry, and the one we recommend:

```sh
git clone https://github.com/CodeXX-DTDK/codexx_rules_registry
cp -r codexx_rules_registry/rules/codegen/codexx/ToString my-project/.codegen/rules/
cd my-project
codegen -a ToString -i include/app/color.hpp
```

A rule is a handful of text files. Vendoring it means it lives in your repository, shows
up in your diffs, and your build depends on nothing remote.

You can also point `-r` at a **vendor directory** without copying — a vendor directory is
a rules root:

```sh
codegen -r ../codexx_rules_registry/rules/codegen/codexx -a ToString -i include/app/color.hpp
```

`-r` is the rules root (default `.codegen/rules`), `-a` names the rule to apply and is
repeatable. The rule's directory name is also the C++ attribute token it matches —
`[[codegen::ToString]]`.

> **Run it from your project, not from this repo.** `codegen` resolves includes, defines,
> and the C++ standard from the *workspace it is invoked in* — your CMake configuration or
> your `codexx.workspace.yaml`. This repository ships its own `codexx.workspace.yaml` so
> that a rule's bundled `input.hpp` sample can be run here; that file covers the samples
> and nothing else.

## The catalog

[`index.json`](./index.json) is the machine-readable catalog, regenerated by CI on every
merge. Fetch it raw; you don't need to clone to see what's available.

## Anatomy of a published rule

| File | Purpose |
|---|---|
| `rule.json` | registry manifest — identity, version, authors, `codegen` compatibility |
| `README.md` | what it generates, how to trigger it, what comes out |
| `LICENSE` | verbatim copy of this repo's MIT license, so the grant travels with the rule |
| `config.yaml` | output language + rule options |
| `transform.luau` | the rule logic — turns a parsed entity into generated source |
| `preamble.luau` | text prepended once per generated file (e.g. `#include`s) |
| `grouping.luau` | *optional* — routes entities to output paths |
| `input.hpp` | *optional* — sample C++ the rule runs against |

`codegen` reads only the four engine files and ignores the rest, so a rule directory
works whether or not it came from here.

## Publishing a rule

Read [CONTRIBUTING.md](./CONTRIBUTING.md). The short version: fork, add one directory
under `rules/codegen/<your-vendor>/`, run the validator, open a PR.

```sh
python3 scripts/validate_registry.py
```

CI runs that same script, so a green local run means a green PR.

## Versioning

Each rule carries its own `version` in `rule.json` — plain semver, no channels. The
directory always holds the current version; every released version is an immutable git
tag:

```
codegen/<vendor>.<RuleName>@MAJOR.MINOR.PATCH
```

To pin an older version, check out its tag. Tags are never deleted. A withdrawn rule is
marked `"yanked": true` rather than removed, so anything already pinned keeps working.

## Editing a rule

**Rules are meant to be edited.** A rule encodes one project's conventions; adapting one
to yours is the expected use, not an edge case.

Everything here is MIT, so you may modify a rule and redistribute it — including under
different licensing terms — provided you keep the MIT notice and the original authors'
copyright, as the MIT license requires. Authors are listed in each rule's `rule.json`
and `README.md`.

Once you've edited a rule it is yours; it will not be updated when the registry copy is.

## Trust

Rules are Luau scripts that run inside `codegen`'s
[sandbox](https://www.codexx-dtdk.com/docs/rules/luau-sandbox). Filesystem, network, and
environment access are opt-in per rule and declared in `config.yaml`; any rule requesting
them gets a security review before merge and says so in its README.

Review the code before you run it — same as any dependency.
